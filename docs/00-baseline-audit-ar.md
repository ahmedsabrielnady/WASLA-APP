# وصلة — تدقيق خط الأساس للمشروع

**تاريخ التدقيق:** 20 نوفمبر 2026  
**المستودع:** ahmedsabrielnady/WASLA-APP  
**الفرع:** main (المراجعة تمت قبل أي تعديل)  
**درجة التدقيق:** فحص ساكن للملفات المنشورة، وليس اختبار تشغيل أو اختراق.

## 1. ما الموجود فعليًا؟

شجرة الفرع main التي تمت مراجعتها تحتوي على ملفين فقط:

| الملف | الحجم التقريبي | الوصف الفعلي |
|---|---:|---|
| index.html | 50 KB | واجهة عميل أحادية الملف، مع CSS وJavaScript مضمّنين |
| admin.html | 40 KB | واجهة HTML ثانية بها وظائف عرض أطباء وحجز وتسليم؛ ليست لوحة مؤسس محمية |

لا تظهر في المستودع ملفات package.json أو TypeScript أو migrations لقاعدة البيانات أو اختبارات أو إعداد CI/CD أو توثيق استعادة النسخ الاحتياطية. لا يعني ذلك بالضرورة عدم وجود جداول في مشروع Supabase يدويًا؛ بل يعني أن تعريف قاعدة البيانات غير محفوظ وقابل للمراجعة داخل GitHub.

## 2. النتائج مرتبة حسب الخطورة

### حرجة قبل أي استخدام حقيقي

1. **غياب نموذج صلاحيات موثوق:** تسجيل الدخول بالبريد وكلمة المرور موجود في index.html، لكن الكود المراجع لا يقدم نظام أدوار متكاملًا للعميل والطبيب والتاجر والمندوب والمعلم والموظف والمؤسس، ولا تظهر حماية خادمية للوحة المؤسس في admin.html. يجب فرض الصلاحيات في PostgreSQL RLS والخادم، وليس بإخفاء عناصر الواجهة.
2. **بيانات طبية غير منظمة:** الحجز يُخزّن داخل جدول orders عام في نص details بدل سجل appointment مستقل يحتوي الطبيب والمريض والفرع والوقت والحالة والاتفاق والموافقة. هذا لا يكفي لتشغيل ملف طبي أو صلاحيات وصول سريرية.
3. **لا يوجد إثبات لمنع تضارب المواعيد:** لا يظهر قفل/قيد قاعدة بيانات يمنع حجز الموعد نفسه مرتين أو يمنع تداخل مواعيد الطبيب.
4. **فقدان بيانات GPS:** مسار التوصيل يحتفظ بالإحداثيات في متغيرات JavaScript، لكن بيانات الإدخال المرسلة لا تتضمن latitude/longitude؛ يُسجل النص GPS فقط عند عدم وجود عنوان يدوي.
5. **عدم موثوقية نتيجة الحفظ في بعض المسارات:** مسار التسليم ينتظر insert لكنه لا يفحص خاصية error الراجعة من Supabase؛ وقد ينتقل المستخدم إلى واتساب رغم فشل التخزين.
6. **لا يوجد دليل على النسخ الاحتياطي أو الاستعادة:** لا توجد سياسة أو إجراءات موثقة للنسخ الاحتياطي واختبار الاستعادة. هذا خطر غير مقبول قبل تخزين ملفات المرضى أو السجلات المالية.

### عالية

7. **حالات طلب غير موحدة:** يظهر في الكود استخدام قيم مثل pending و«قيد المراجعة» دون آلة حالات موحدة أو قواعد انتقال موثقة.
8. **المنتجات والأسعار ثابتة داخل الواجهة:** بيانات السوق والمنتجات والأسعار ليست كتالوجًا يديره التاجر من قاعدة البيانات.
9. **السلة ليست معاملة تجارية:** السلة في الذاكرة داخل المتصفح ولا يظهر حجز مخزون ذري، أو order_items، أو snapshot للأسعار، أو فصل طلبات المتاجر المختلفة.
10. **الحجز الطبي ليس مرتبطًا بسجل مستخدم موثوق:** يوجد مسار يضيف حجزًا إلى orders دون user_id، ويحوّل التفاصيل إلى واتساب. رقم الطبيب يُقرأ من النموذج لكنه لا يُستخدم كمعرّف مرجعي دائم في سجل الحجز.
11. **بيانات تجريبية قد تظهر كأنها حقيقية:** عند فشل جلب الأطباء توجد دالة fallback تعرض أسماء ورسومًا تجريبية. يجب ألا تعرض بيانات وهمية للمستهلك في بيئة الإنتاج؛ يعرض النظام حالة عدم التوفر بوضوح.
12. **مخاطرة حقن HTML/JavaScript:** بيانات مثل clinic_name واسم الطبيب المجلوبة من قاعدة البيانات تُركّب داخل HTML وداخل معالج onclick نصي. إذا استطاع مزود تعديل هذه القيم فقد ينشأ مسار XSS. يجب استخدام DOM آمن أو مكونات React مع escaping وعدم بناء handlers من نصوص.
13. **لا يوجد سجل مالي:** لا تظهر دفعات أو محاولات دفع أو عمولات أو تسويات مقدمي خدمات أو استردادات أو دفتر قيود غير قابل للتعديل.
14. **المساعد الذكي ليس AI حقيقيًا:** الردود تعتمد على كلمات مفتاحية ومؤقتات ثابتة؛ لا يوجد استدعاء لخدمة ذكاء اصطناعي أو سياسات حماية لمعلومات المستخدمين.

### متوسطة

15. **تجربة الحساب بسيطة جدًا:** بيانات الحساب المعروضة تعتمد على البريد الإلكتروني. لا تظهر رحلة موثقة للتحقق من الهاتف أو إدارة الأجهزة والجلسات أو استعادة الحساب أو الموافقة على الشروط والخصوصية.
16. **الشريط السفلي يعرض عناصر غير منفذة بالكامل:** توجد رسائل «قريبًا» في وظائف مثل طلباتي والمحفظة، لذلك لا ينبغي تقديمها كميزات مكتملة.
17. **الاعتماد على CDN خارجي:** الخطوط والأيقونات ومكتبة Supabase تُحمّل من خدمات خارجية؛ يجب تثبيت الإصدارات ومراجعة الاعتمادية وسياسة الخصوصية والأداء.

## 3. مفاتيح الاتصال

وجود Supabase URL وpublishable/anon key في واجهة المتصفح ليس وحده تسريبًا؛ هذا النوع من المفاتيح مصمم للاستخدام العام. الأمان الحقيقي يعتمد على تفعيل RLS على كل جدول وسياسات دقيقة وعدم وضع service_role أو أي سر خادمي في المتصفح أو GitHub. لم يتمكن هذا التدقيق من قراءة سياسات RLS أو مخطط مشروع Supabase الحي، ولذلك لا يصدر حكمًا بأن قاعدة البيانات آمنة أو غير آمنة.

## 4. ما لم يتم اختباره

لم يتم تشغيل الموقع في متصفح أو الاتصال بمشروع Supabase أو تنفيذ حجز حقيقي؛ لذلك لا ندعي نجاحًا أو فشلًا تشغيليًا. لم تظهر في المستودع بيئة تشغيل أو اختبارات آلية يمكن تشغيلها من هنا. هذا الفحص ساكن للكود المنشور فقط.

## 5. بوابة الخروج من مرحلة التدقيق

لا يبدأ إطلاق تجاري قبل تحقق جميع البنود التالية:

- تعريف جميع جداول قاعدة البيانات وترحيلاتها داخل المستودع.
- RLS مُفعّل ومختبر لكل جدول وStorage bucket.
- أدوار وصلاحيات خادمية، مع حساب مؤسس محمي بـ MFA وسجل تدقيق.
- حجز مواعيد ذري يمنع التداخل وإعادة الإرسال المكرر.
- سلة وطلبات ومخزون وأسعار محفوظة على الخادم.
- GPS وعناوين الاستلام والتسليم محفوظة بشكل صحيح.
- حالات تشغيلية ومالية محددة ومقيدة.
- نسخ احتياطي مستقل واختبار استعادة ناجح.
- اختبارات تسجيل ودخول وخروج وصلاحيات وطلبات وحجز ودفع وإلغاء.
- سياسة خصوصية وموافقة صريحة ومعالجة متوافقة لبيانات الصحة والأطفال.
