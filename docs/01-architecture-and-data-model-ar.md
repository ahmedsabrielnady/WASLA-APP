# وصلة — المعمارية البرمجية ونموذج البيانات

## 1. القرار المعماري

**الاختيار المقترح:** Modular Monolith، وليس Microservices في البداية.

السبب: فريق صغير ومدينة إطلاق واحدة وعدد كبير من المجالات. الخدمات المصغرة ستضيف تشغيلًا ونشرًا ومراقبة وتكلفة واتصالات شبكية قبل وجود حجم يبررها. نبدأ بتطبيق واحد مقسّم إلى وحدات نطاقية مستقلة، ونفصل خدمة لاحقًا فقط إذا أثبتت مؤشرات الحمل والحاجة ذلك.

### التقنية المبدئية

- Frontend: React + TypeScript + Vite، واجهة عربية RTL وPWA.
- UI: مكونات قابلة لإعادة الاستخدام ونظام تصميم موحد.
- Validation: مخططات تحقق مشتركة للواجهة والخادم.
- Backend/Data: PostgreSQL في Supabase الحالي بعد تدقيق مخططه وRLS.
- Auth: Supabase Auth أو موفر بديل بعد حسم استراتيجية الهاتف والتحقق.
- Server logic: PostgreSQL functions/RPC وEdge Functions للعمليات الحساسة.
- Storage: ملفات خاصة مع signed URLs قصيرة الصلاحية؛ لا توجد روابط عامة لملفات المرضى.
- Hosting: Cloudflare Pages مبدئيًا للواجهة. GitHub هو مستودع المصدر وCI، وليس استضافة تجارية عبر GitHub Pages.
- Tests: Vitest للوحدات، Playwright للتدفق الكامل، واختبارات SQL/RLS.

هذا اختيار قابل للمراجعة وليس أمرًا بتغيير قاعدة البيانات قبل فحصها.

## 2. حدود الوحدات

1. Identity & Access: الحسابات، الأدوار، العضويات، الموافقات، الجلسات.
2. Provider Directory: مقدمو الخدمات، التراخيص، الفروع، مناطق التغطية، ساعات العمل.
3. Marketplace: المتاجر، المنتجات، المتغيرات، الأسعار، المخزون، السلة.
4. Orders & Fulfillment: الطلبات، البنود، التقسيم حسب المتجر، التوصيل، حالات التنفيذ.
5. Healthcare: الأطباء، العيادات، الجداول، الحجوزات، الطوابير، ملفات المرضى، التحاليل والأشعة والوصفات.
6. Education: المعلمون، المواد، الدورات، الحصص، الطلاب، أولياء الأمور والتسجيل.
7. Home Services: طلب الصيانة، المعاينة، عروض الأسعار، الموافقة، إتمام المهمة.
8. Mobility: خدمات السيارات، الحجوزات، فحص الأعطال، البطارية والإطارات والغسيل.
9. Delivery: الشحنات، نقاط الاستلام والتسليم، التسعير، تعيين المندوب وإثبات التسليم.
10. Money: المدفوعات، العمولات، الرسوم، المبالغ المستردة، مستحقات الشركاء والتسويات.
11. Notifications: إشعارات داخل التطبيق والبريد وWhatsApp/SMS حسب تكاليف وموافقات القنوات.
12. Founder Operations: الموافقات، إدارة القطاعات، الشكاوى، التسويات، التقارير، سجل التدقيق.

## 3. نموذج البيانات المقترح

يجب عدم وضع كل شيء في جدول orders بحقل نصي واحد. الجداول التالية تمثل حدودًا منطقية؛ أسماءها النهائية تتحدد بعد فحص قاعدة Supabase الحالية.

### الهوية والجهات

- profiles: بيانات المستخدم الأساسية.
- roles وuser_roles: الأدوار، مع السماح للمستخدم بأكثر من دور.
- organizations: العيادة أو المتجر أو شركة الصيانة.
- organization_members: أعضاء المنشأة وأدوارهم.
- provider_profiles: البيانات المهنية والتحقق.
- provider_branches: الفروع والمواقع وساعات العمل.
- provider_services: الخدمات والأسعار ومناطق التغطية.
- customer_addresses: عناوين العميل ونقاطه الجغرافية.
- consents: نسخة الموافقة، الغرض، النص، وقت القبول، وسحب الموافقة.

### السوق والطلبات

- stores, products, product_variants, product_prices.
- inventory_balances وinventory_movements.
- carts وcart_items.
- orders وorder_items وorder_fulfillments.
- order_status_events: سجل انتقالات الحالة، لا يتم استبداله عند كل تحديث.
- shipments: بيانات الشحنة والإحداثيات والعناوين.
- service_requests وservice_quotes وservice_jobs للصيانة والسيارات والخدمات المنزلية.

### الصحة

- doctor_profiles وclinic_profiles.
- doctor_specialties وdoctor_clinic_memberships.
- doctor_schedules وavailability_blocks.
- appointments: الطبيب والمريض والفرع ووقت البداية والنهاية والحالة والرسوم.
- appointment_events وqueue_events.
- patient_profiles وpatient_records وmedical_documents.
- prescriptions وprescription_items.
- lab_orders وimaging_orders وprovider_results.
- patient_access_grants وmedical_access_logs.

البيانات الطبية ليست حقلًا نصيًا مشتركًا. كل قراءة أو تعديل لملف مريض يجب أن يكون له سبب وصلاحية وسجل وصول. ولا تستخدم بيانات المرضى لتدريب ذكاء اصطناعي أو لإرسالها إلى خدمات طرف ثالث دون أساس قانوني وموافقة محددة.

### التعليم

- teacher_profiles وsubjects وgrade_levels.
- courses وcourse_sessions.
- enrollments وstudent_guardians.
- assignments وlearning_resources، عند الحاجة.
- لا يُنشأ حساب طفل مستقل دون تصميم موافقة ولي الأمر وحماية بيانات القاصر.

### المال

- payment_intents وpayment_attempts.
- payments وrefunds.
- commission_rules وcommission_accruals.
- provider_settlements وsettlement_items.
- ledger_accounts وledger_entries.
- cash_collections وcourier_cash_reconciliations.

يجب أن يكون دفتر القيود مزدوج القيد أو على الأقل سجلًا ماليًا متوازنًا وغير قابل للمحو الصامت. التصحيح يتم بقيود عكسية، وليس حذف السجل الأصلي.

## 4. قواعد تمنع ضياع البيانات والتكرار

- لا تستخدم الحذف المادي لطلبات مكتملة أو قيود مالية أو سجلات تدقيق.
- استخدم deleted_at للأرشفة عند السماح قانونيًا، مع سياسة احتفاظ وحذف نهائي محددة وفق نوع البيانات والقانون.
- استخدم UUID للمعرفات العامة، وcreated_at وupdated_at وcreated_by وupdated_by.
- لكل طلب مفتاح idempotency لمنع الطلب المكرر عند إعادة الضغط أو انقطاع الشبكة.
- احتفظ بسعر واسم المنتج والضريبة والعمولة وقت الشراء كنسخة تاريخية داخل order_items.
- خصم المخزون وحجزه يجب أن يحدثا ذريًا في transaction أو RPC، لا في كود المتصفح.
- لا تسمح بتعديل سجل مالي مكتمل؛ أنشئ refund أو reversal.
- أنشئ migrations مرقمة في GitHub، ولا تعدّل قاعدة الإنتاج يدويًا دون migration قابلة للتكرار والمراجعة.
- اختبر الاستعادة من نسخة احتياطية دوريًا. وجود نسخة احتياطية دون اختبار restore ليس خطة استعادة.

## 5. الصلاحيات

- Customer: يرى ملفه وعناوينه وطلباته فقط.
- Provider Owner: يدير منشأته وفروعها وكتالوجها وفريقها.
- Doctor: يرى الحجوزات والسجلات التي يجيزها المريض والسياسة الطبية فقط.
- Clinic Staff: صلاحيات تشغيلية محددة، دون صلاحية افتراضية لقراءة كل السجل الطبي.
- Teacher: يرى طلاب حصصه والبيانات اللازمة للتعليم.
- Driver: يرى بيانات المهمة الحالية فقط، وليس كامل ملفات العملاء.
- Founder: صلاحيات منصة إدارية منفصلة، مع MFA وسجل تدقيق. لا تعني صفة المؤسس إتاحة غير مبررة لكل تفاصيل السجل الطبي.
- Support: يرى بيانات الطلب الضرورية للدعم مع إخفاء البيانات الصحية الحساسة.

**قاعدة أمنية:** كل صلاحية تُفرض في قاعدة البيانات والخادم. الواجهة تعرض ما تسمح به الصلاحية فقط ولا تنشئها.

## 6. حالات الطلب والحجز

الحالة ليست نصًا حرًا. تستخدم قائمة انتقالات محددة، مثال السوق:

draft → placed → accepted → preparing → ready_for_pickup → assigned → picked_up → delivered → completed

والاستثناءات: rejected، cancelled، failed، refund_pending، refunded.

لا يسمح الانتقال العشوائي بين الحالات. كل انتقال يسجل الفاعل والوقت والسبب. الحجز الطبي له آلة حالات منفصلة، وكذلك الصيانة والتعليم والتوصيل.

## 7. تتبع الأحداث والإشعارات

تُنشأ أحداث موثوقة عند:
- تأكيد حجز أو قرب موعده.
- اقتراب دور المريض.
- قبول الطلب أو بدء تجهيزه أو خروجه للتوصيل.
- تعيين المندوب أو وصوله أو إتمام التسليم.
- قبول عرض سعر الصيانة أو إتمام المهمة.
- استحقاق مبلغ لمقدم خدمة أو فشل تسوية.

يفصل النظام بين event creation وnotification delivery؛ ففشل إرسال رسالة لا يلغي الطلب. تسجل محاولات الإرسال وإعادة المحاولة مع منع التكرار.

## 8. محرك الذكاء الاصطناعي

يبدأ بمساعد بحث وتنقل ودعم يعتمد على كتالوج وصلة وقاعدة معرفة معتمدة. لا يشخّص المرض، ولا يصف دواء، ولا يقرر الأهلية التأمينية وحده. أي تلخيص طبي يجب أن يعرض مصدره ويطلب مراجعة بشرية، مع منع إرسال البيانات الحساسة لمزود AI دون موافقة وعقد وضوابط قانونية.
